# Checkpoint 4 — Tier 3 CP Games Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the last three engine-driven CP games — `shapes`, `parity`, `ordering` — plus one new pure renderer (`js/render/shapes.js`), completing the twelve-game programme, with **no change to `js/engine/game-engine.js`**.

**Architecture:** Each game is a plain object in `js/games/<id>.js` with a pure `generate(difficulty, ctx)` returning exercise objects, registered in `js/engine/registry.js`. `GameEngine` already owns the session loop, scoring, celebration and persistence. `shapes` and `parity` use only `layoutClass`, `choiceClass`, object-form `choices` (`{ value, html }`) and `exercise.bodyClass`. `ordering` is the project's first **sequencing** interaction and uses the existing `renderChoices` seam with a one-submission-per-attempt discipline — see "The `ordering` design question, resolved" below. `shapes` is the first and only game in the `geometrie` domain, so that group appears in the chooser for the first time (`gamesByDomain()` filters out empty domains).

**Tech Stack:** Plain ES modules (no bundler, no transpilation), Vitest + jsdom for tests, CSS in the single `css/game.css`, translations in `js/i18n/translations.js`, service worker generated by `tools/build-sw.js`.

## Global Constraints

Every task's requirements implicitly include this section.

- **The `ctx` purity rule** (verbatim from `CLAUDE.md`). A game's `generate` must be **pure**: no `Math.random`, no `I18n`, no DOM access, no `Date`.
  - `ctx.rng` is the only source of randomness — normally `Math.random`, but tests inject a seeded rng, so `generate` must call `ctx.rng()` and never `Math.random()` directly.
  - `ctx.t` is the only source of translated strings — `(key, params) => I18n.t(key, params)` — so `generate` must call `ctx.t(...)` and never `I18n` directly.
  - `ctx.lang` is the active language code, for anything language-dependent that isn't a plain translation lookup. **No game in this checkpoint needs it.**
  - `ctx.count` is the already-resolved round count for the chosen difficulty (`GameEngine.resolveCount` reads `game.rounds[difficulty]`) — `generate` must use `ctx.count` and never read `game.rounds` itself, or a picker game and a fixed-rounds game would silently diverge.
  - `ctx.category` is set only for `setup: 'category'` games. **None of the three games in this checkpoint uses it, and none gets a pre-screen.**
  - The purity rule binds `generate` only. `ordering`'s `renderChoices` is an interaction handler, not a generator: it touches the DOM and uses `setTimeout` by design, exactly as `chess.renderPrompt` and `uno.renderChoices` already do.
- **No frameworks, no bundler, no transpilation** — keep it plain ES that runs directly in the browser. Match the existing style (2-space indent in `js/`, single quotes, string-concatenated HTML). Note `js/i18n/translations.js` is the one file indented with **4 spaces** — match the file you are editing. In `translations.js`, a value containing an apostrophe is written with **double quotes** (`ordering: "Ranger dans l'ordre"`); follow that convention rather than backslash-escaping.
- **Wrong-answer pattern** (verbatim from `CLAUDE.md`): mark the button `.wrong`, set `dataset.wrongChoice`, play `Sound.play('wrong')`, and let the player retry; advance on the correct choice. This is implemented inside `GameEngine.answer()`. `shapes` and `parity` get it for free through the default choice rendering and must not reimplement any of it. `ordering` renders its own tiles, so it adds the `.wrong` class and the retry itself while still letting the **engine** count the attempt and play the sound — it must never call `Sound` directly, and it must never set `dataset.wrongChoice` (see the design finding below).
- **`sw.js` is generated** — never hand-edit it, and never hand-bump `CACHE_VERSION`. Run `npm run build:sw` (`tools/build-sw.js`), which scans `js/`, `css/`, `images/`, and `flags/` for the asset list and computes the next `CACHE_VERSION` itself (same day → bump the counter, new day → reset to `01`). A hand-edit to `sw.js` will be silently overwritten the next time the build runs. **`test/tools/build-sw.test.js` fails the moment a new file under `js/` is committed without regenerating `sw.js`, so every task that adds a `js/` file must run `npm run build:sw` before committing.**
- **`test/i18n/no-dead-keys.test.js` asserts all five language blocks have an identical key set**, so a key added to one block must be added to all five in the same commit. `test/i18n/diacritics.test.js` asserts the French block has no unaccented remnants — write French correctly accented, including the space before `?` that the existing French strings use (`'Combien cela fait-il ?'`).
- **No new `GameEngine` seams, and no edit to `js/engine/game-engine.js`.** Checkpoints 2 and 3 each needed zero engine changes; so does this one. Every game must fit the existing contract. If a game appears to need a new seam, stop and report it rather than inventing one.
- **CSS append rule.** `css/game.css` now ends with **ten separately appended `@media (orientation: landscape)` blocks** (at lines 1604, 1804, 1850, 1919, 1974, 2007, 2055, 2090, 2140 and 2163 as of the start of this checkpoint). Do **not** edit inside any existing one. Each task appends its own portrait rules and then a **new** `@media (orientation: landscape) { ... }` block at the very end of the file. Multiple media blocks are valid CSS, later rules win, and appending keeps each task independently committable.
- **CSS scoping rule.** A game's choice-button rule must be **scoped to its layout class** — write `.parity-layout .parity-choice-btn { ... }`, never a bare `.parity-choice-btn { ... }`. Checkpoint 3's final review found two unscoped single-class rules (`.compare-choice-btn`, `.tens-units-choice-btn`) winning only on source order, which is a latent bug the moment anything is appended after them. Every new rule in this checkpoint carries its layout-class prefix.
- **Testing discipline** (verbatim intent from `CLAUDE.md`). Prove a new test can fail before trusting it: break the code it names, confirm the test goes red, then restore the code and confirm `git diff` is empty. If a test depends on randomness, either seed the rng and assert an exact result, or run the mutation **10 times** and require red on all ten — a guard that only sometimes catches its mutation is worse than no guard. Prefer asserting the property over the implementation.
- **No test may import a constant from the module it is guarding in order to build its own expectation.** Checkpoint 3 shipped a tautological ladder guard that way — a test asserting `>= MIN_TWO_STEP_TOTAL` while the generator floored on that same constant, which left all 17 tests green when the constant was lowered to a broken value. Guards state their expected value as an **independent literal, deliberately duplicated**, with a comment saying why. Importing a constant in order to compare it *against* a literal (`expect(SHAPE_SIDES).toEqual({ square: 4, ... })`) is the opposite and is required; deriving the expectation *from* it (`expect(pointCount).toBe(SHAPE_SIDES[shape])`) is banned.
- **No test may cover only a sample of a space the code enumerates.** Checkpoint 3's `numberToWords` tests passed with 44 wrong words because only ~13 of 100 forms per language were pinned. The shape vocabulary is five members and the rotation/scale policy is a short fixed list — **pin all of it**, every shape, every rotation, every scale.
- **Every game gets `rounds: { easy: 5, normal: 10, hard: 20 }`**, no pre-screen. `parity` and `ordering` get `domain: 'nombres'`; `shapes` gets `domain: 'geometrie'` and is the **first and only** game in that domain.
- **Emoji must stay unique across `GAMES`.** `👯` is already taken by `doubles` and `🔢` by `count_objects`, so this checkpoint uses `📐` (shapes), `🧦` (parity — socks come in pairs) and `🪜` (ordering).
- **Workflow.** This checkpoint runs on a branch in this worktree; it merges to `main` once green. Run `npm test` before every commit; never commit a red suite.

## The `ordering` design question, resolved

`ordering` asks the child to tap 3–5 numbers in sequence. Every other game in the app asks for one tap. `CLAUDE.md` documents the hazard from checkpoint 1: `GameEngine.answer()` latches a wrong choice via `dataset.wrongChoice` and thereafter only re-shakes it, never re-judging it — which is precisely why `memory` had to become `legacy: true`, since each of its tiles must eventually be tapped *correctly* and the first wrong tap made the board uncompletable.

**Resolution: route 1 — `ordering` fits the existing seams, with no engine change and no `legacy: true`.** This was verified by running an `ordering`-shaped stub game through the real `GameEngine` in jsdom, not by reading the docs. Here is exactly why the latch is not reached, quoting `js/engine/game-engine.js:131-173`:

```js
  answer(value, btn) {
    if (this.advancing) return;

    if (btn && btn.dataset.wrongChoice) {
      ...
      return;
    }
    ...
    this.wrongAttempts++;
    if (btn) {
      btn.classList.add('wrong');
      btn.dataset.wrongChoice = '1';
    }
    Sound.play('wrong');
  },
```

- `showExercise` builds `const submit = (value, btn) => this.answer(value, btn);` (line 74) and hands it to `renderChoices`. **The `btn` argument is optional.** `chess` and `uno` both pass one; `ordering` deliberately passes none.
- With `btn === undefined`, `if (btn && btn.dataset.wrongChoice)` is falsy, so **the latch branch is never entered**, and `if (btn) { btn.dataset.wrongChoice = '1'; }` never runs, so **nothing is ever latched in the first place**. The wall `memory` hit is a per-button wall; `ordering` never gives the engine a button.
- **What passing a button would actually cost, measured rather than assumed.** The mutation was run against the real engine while writing this plan, and it does *not* deadlock `ordering` the way it deadlocked `memory` — `memory` routed each tile's acceptance through the engine, whereas `ordering` decides for itself which taps it accepts, so a latched tile is still tappable as part of a correct sequence. What it does instead is corrupt scoring, silently: the game's own reset clears `.wrong` but has no business clearing the engine's private `dataset.wrongChoice`, so every wrong tap of that tile after the first is swallowed by the latch branch and returns before `wrongAttempts++`. Three genuine wrong attempts score as one, with nothing on screen to show for it. So the reason to pass no button is not "otherwise it hangs" but "otherwise the engine keeps per-button state about an interaction that has no per-button semantics". Task 4's Step 13 reproduces this exactly (`expected 1 to be 3`).
- `ordering.renderChoices` accumulates the child's taps in a closure and calls `submit(...)` **exactly once per attempt**: once with the complete ordering when the sequence is finished, or once with the wrong-ending prefix the moment a tap breaks the sequence. So the engine sees one judgement per attempt, exactly like a single-choice game.
- On a wrong attempt the engine increments `wrongAttempts` and plays `Sound.play('wrong')`, then returns without re-rendering. The DOM is left exactly as the game left it, so **the game owns the reset** — it clears its own tap state and `.wrong`/`.picked` classes after a short delay and the child retries the whole sequence. Because nothing is latched, the exercise stays completable indefinitely.
- On a correct attempt the engine plays `Sound.play('correct')`, sets `this.advancing = true` (which makes every further tap a no-op — the double-tap guard covers a sequencing game just as well as a single-choice one), and advances after `advanceDelayMs`. `if (btn) btn.classList.add(...)` is skipped, so the game applies its own `.correct` styling before submitting.

**No `isCorrect` seam is needed either.** `correctAnswer` is the required ordering joined with commas (`'2,5,9'`), and the game submits the tapped ordering joined the same way, so the engine's default `value === exercise.correctAnswer` is already an exact comparison of the two orderings. A wrong submission can never collide with it: a wrong-ending prefix is either shorter than `correctAnswer` or the same length with a different final element. `CLAUDE.md` says to define a seam "only if the default doesn't fit" — the default fits, so `ordering` defines `renderChoices` and nothing else.

**One behavioural difference, accepted deliberately.** In a single-choice game, re-tapping an already-wrong button re-shakes it without re-counting. In `ordering` every attempt is a fresh full sequence, so every wrong attempt counts. That is the correct semantics for this game and needs no engine support.

**The wrong-attempt feedback contract** (satisfying `CLAUDE.md`'s wrong-answer pattern in spirit):

1. The tile that broke the sequence gets `.wrong`. Because the tile also carries the base `.choice-btn` class, it picks up the existing `.choice-btn.wrong { background: #f44336; animation: shake 0.4s ease; }` rule for free — the child sees the same red shake as everywhere else in the app.
2. `submit(...)` is called once, so the engine plays the wrong sound and counts one attempt. The game never calls `Sound` itself.
3. The board locks for `RESET_DELAY_MS` (500 ms) so the red shake is visible, then clears every tile's `.wrong`, `.picked` and rank badge and unlocks. The child restarts the sequence from the smallest (or largest) number.
4. Nothing is disabled, greyed out or latched, so the exercise is always completable.

## The two shuffle-test shapes

Every game task below carries a shuffle test. There are two valid shapes and each task states which one applies and why. This distinction is load-bearing: checkpoint 2 shipped a shuffle test that was **vacuous** and had to be rewritten (see `test/games/compare.test.js:73-88`).

- **Shape A — ungrouped `indexOf`.** Valid only when the correct answer's *pre-shuffle* position is a **fixed, known index**. Deleting the shuffle then pins `indexOf(correctAnswer)` to that one index, `positions.size` collapses to `1`, and the assertion goes red deterministically.
- **Shape B — positions grouped per correct-answer value.** Required when the pre-shuffle position is *not* fixed. `compare` builds from a constant `SIGNS = [lt, eq, gt]` array while `correctAnswer` varies, so an ungrouped `indexOf` finds three different positions even with the shuffle deleted — vacuous. Grouping by the answer's value and requiring *each group* to show more than one position is what actually proves shuffling.

Which applies where in this checkpoint:

| Game | Shape | Why |
|---|---|---|
| `shapes` | **B**, all three bands | Choices come from a fixed list (`SHAPE_KEYS` on easy/hard, `COUNT_CHOICES` on normal) while the answer varies, so ungrouped `indexOf` is vacuous — the `compare` situation exactly. |
| `parity` | **B**, mandatory and non-negotiable | Only **two** fixed choices. Ungrouped, `indexOf(correctAnswer)` is `0` for `'even'` and `1` for `'odd'` *with the shuffle deleted*, so the position set is `{0, 1}` and the test passes on unshuffled code. This is the sharpest vacuity trap in the project. |
| `ordering` | **A**, measured **per difficulty** | `numbers` is a shuffle of the sorted draw, so without the shuffle the first required number sits at a fixed index — `0` on the ascending bands, `size - 1` on the descending one. Pooling the bands would collect `{0, 4}` and pass vacuously, so each difficulty is measured in its own `Set`. |

### Task 1: ShapeRenderer

**Files:**
- Create: `js/render/shapes.js`
- Test: `test/render/shapes.test.js`
- Modify: `sw.js` (via `npm run build:sw`, never by hand)

**Interfaces:**
- Consumes: nothing.
- Produces, all named exports of `js/render/shapes.js`:
  - `SHAPE_KEYS = ['square', 'rectangle', 'triangle', 'circle', 'rhombus']` — the CP shape vocabulary in display order (`carré`, `rectangle`, `triangle`, `cercle`, `losange`).
  - `SHAPE_SIDES = { square: 4, rectangle: 4, triangle: 3, circle: 0, rhombus: 4 }`.
  - `SHAPE_CORNERS = { square: 4, rectangle: 4, triangle: 3, circle: 0, rhombus: 4 }`.
  - `ShapeRenderer.render(shape, options) -> string`. `options` is `{ rotate, scale, fill, stroke }`, all optional (`rotate` in degrees, default `0`; `scale` a positive multiplier, default `1`). Returns an SVG string sized `200 × 200` with `class="shape-figure dice-enter"`, `data-shape`, `data-rotate` and `data-scale` attributes. The four polygons render as one `<polygon class="shape-poly" points="...">` whose point count equals the shape's corner count; the circle renders as one `<circle class="shape-circle">`. An unrecognised shape renders as `data-shape="unknown"` with **no figure at all**, so a typo shows as a blank rather than a plausible circle (the same defensive choice `CoinRenderer` makes for a non-euro denomination). Rotation and scale are **baked into the coordinates**, not applied as an SVG `transform`, and every shape is normalised to a circumradius of `60 × scale`, so the figure is guaranteed to stay inside the frame at every rotation and every scale up to 1.5. No DOM access, no randomness. Task 2 (`shapes`) is the only consumer.

- [ ] **Step 1: Write the failing test**

Create `test/render/shapes.test.js`:

```js
import { describe, it, expect } from 'vitest';
import { ShapeRenderer, SHAPE_KEYS, SHAPE_SIDES, SHAPE_CORNERS } from '../../js/render/shapes.js';

// Every rotation the game could ever ask for, and the full scale range, so the
// frame-containment and rigidity properties are proven over the whole space the
// renderer supports rather than a sample of it.
const ALL_ROTATIONS = [];
for (let deg = 0; deg < 360; deg += 15) ALL_ROTATIONS.push(deg);
const ALL_SCALES = [0.6, 0.75, 1, 1.3, 1.5];

// Deliberately duplicated literals, NOT derived from SHAPE_SIDES/SHAPE_CORNERS.
// A test that reads its expectation out of the module under test cannot fail
// when that module's table is wrong.
const EXPECTED_KEYS = ['square', 'rectangle', 'triangle', 'circle', 'rhombus'];
const EXPECTED_SIDES = { square: 4, rectangle: 4, triangle: 3, circle: 0, rhombus: 4 };
const EXPECTED_CORNERS = { square: 4, rectangle: 4, triangle: 3, circle: 0, rhombus: 4 };

function points(html) {
  const match = /points="([^"]+)"/.exec(html);
  if (!match) return [];

  return match[1].split(' ').map(pair => pair.split(',').map(Number));
}

function circleGeometry(html) {
  const match = /class="shape-circle" cx="(\d+)" cy="(\d+)" r="([\d.]+)"/.exec(html);

  return match ? { cx: Number(match[1]), cy: Number(match[2]), r: Number(match[3]) } : null;
}

function maxRadius(html) {
  const circle = circleGeometry(html);
  if (circle) return circle.r;

  return Math.max(...points(html).map(([x, y]) => Math.hypot(x - 100, y - 100)));
}

function extremes(html) {
  const circle = circleGeometry(html);
  if (circle) return { min: circle.cx - circle.r, max: circle.cx + circle.r };

  const all = points(html).flat();

  return { min: Math.min(...all), max: Math.max(...all) };
}

function diagonals(html) {
  const p = points(html);

  return [
    Math.hypot(p[0][0] - p[2][0], p[0][1] - p[2][1]),
    Math.hypot(p[1][0] - p[3][0], p[1][1] - p[3][1]),
  ];
}

describe('shape vocabulary tables', () => {
  it('covers exactly the five CP shapes, in display order', () => {
    expect(SHAPE_KEYS).toEqual(EXPECTED_KEYS);
  });

  it('states the side and corner count of every shape', () => {
    expect(SHAPE_SIDES).toEqual(EXPECTED_SIDES);
    expect(SHAPE_CORNERS).toEqual(EXPECTED_CORNERS);
  });
});

describe('ShapeRenderer', () => {
  it('returns an svg string carrying the figure class for every shape', () => {
    for (const shape of EXPECTED_KEYS) {
      const html = ShapeRenderer.render(shape);
      expect(html).toMatch(/^<svg /);
      expect(html).toContain('class="shape-figure dice-enter"');
      expect(html).toContain('data-shape="' + shape + '"');
      expect(html).toContain('viewBox="0 0 200 200"');
    }
  });

  it('reports the rotation and scale it was asked for', () => {
    const html = ShapeRenderer.render('triangle', { rotate: 75, scale: 1.3 });
    expect(html).toContain('data-rotate="75"');
    expect(html).toContain('data-scale="1.3"');
    expect(ShapeRenderer.render('triangle')).toContain('data-rotate="0"');
    expect(ShapeRenderer.render('triangle')).toContain('data-scale="1"');
  });

  it('pins the exact untransformed geometry of the whole vocabulary', () => {
    // The full enumerable set, not a sample: five shapes, all of them pinned.
    expect(ShapeRenderer.render('square')).toContain(
      'points="57.57,57.57 142.43,57.57 142.43,142.43 57.57,142.43"');
    expect(ShapeRenderer.render('rectangle')).toContain(
      'points="47.91,70.23 152.09,70.23 152.09,129.77 47.91,129.77"');
    expect(ShapeRenderer.render('triangle')).toContain(
      'points="100,40 151.96,130 48.04,130"');
    expect(ShapeRenderer.render('rhombus')).toContain(
      'points="100,40 136,100 100,160 64,100"');
    expect(ShapeRenderer.render('circle')).toContain(
      '<circle class="shape-circle" cx="100" cy="100" r="60"');
  });

  it('draws a figure with exactly as many corners as the shape has', () => {
    // The trap: a "triangle" drawn with four points, or a "square" with three.
    for (const shape of ['square', 'rectangle', 'triangle', 'rhombus']) {
      expect(points(ShapeRenderer.render(shape))).toHaveLength(EXPECTED_CORNERS[shape]);
      expect(ShapeRenderer.render(shape)).toContain('class="shape-poly"');
      expect(ShapeRenderer.render(shape)).not.toContain('class="shape-circle"');
    }
    const circle = ShapeRenderer.render('circle');
    expect(circle).toContain('class="shape-circle"');
    expect(circle).not.toContain('<polygon');
    expect(points(circle)).toHaveLength(EXPECTED_CORNERS.circle);
  });

  it('keeps the corner count under every rotation and scale', () => {
    for (const shape of ['square', 'rectangle', 'triangle', 'rhombus']) {
      for (const rotate of ALL_ROTATIONS) {
        for (const scale of ALL_SCALES) {
          expect(points(ShapeRenderer.render(shape, { rotate, scale })))
            .toHaveLength(EXPECTED_CORNERS[shape]);
        }
      }
    }
  });

  it('renders an unrecognised shape as an empty frame, not a plausible circle', () => {
    const html = ShapeRenderer.render('hexagon');
    expect(html).toContain('data-shape="unknown"');
    expect(html).not.toContain('<polygon');
    expect(html).not.toContain('<circle');
  });

  it('never lets any shape leave the frame, at any rotation and any scale', () => {
    // Full enumeration: 5 shapes x 24 rotations x 5 scales. A shape clipped by
    // the viewBox reads as a different shape to a six-year-old.
    for (const shape of EXPECTED_KEYS) {
      for (const rotate of ALL_ROTATIONS) {
        for (const scale of ALL_SCALES) {
          const { min, max } = extremes(ShapeRenderer.render(shape, { rotate, scale }));
          expect(min).toBeGreaterThanOrEqual(10);
          expect(max).toBeLessThanOrEqual(190);
        }
      }
    }
  });

  it('rotates rigidly: the circumradius is 60 x scale whatever the rotation', () => {
    for (const shape of EXPECTED_KEYS) {
      for (const rotate of ALL_ROTATIONS) {
        for (const scale of ALL_SCALES) {
          const radius = maxRadius(ShapeRenderer.render(shape, { rotate, scale }));
          expect(Math.abs(radius - 60 * scale)).toBeLessThan(0.05);
        }
      }
    }
  });

  it('rescales linearly', () => {
    for (const shape of EXPECTED_KEYS) {
      const small = maxRadius(ShapeRenderer.render(shape, { scale: 1 }));
      const large = maxRadius(ShapeRenderer.render(shape, { scale: 1.5 }));
      expect(large / small).toBeCloseTo(1.5, 3);
    }
  });

  it('actually turns the figure rather than only labelling it rotated', () => {
    // An unrotated square is flat-bottomed: two corners share the lowest y. At
    // 30 degrees no two corners share a y at all. That difference is the whole
    // pedagogical point of the hard band, so it gets its own assertion.
    const flat = points(ShapeRenderer.render('square'));
    const flatYs = flat.map(([, y]) => y);
    expect(new Set(flatYs).size).toBe(2);
    expect(flatYs.filter(y => y === Math.max(...flatYs))).toHaveLength(2);

    const turned = points(ShapeRenderer.render('square', { rotate: 30 }));
    expect(new Set(turned.map(([, y]) => y)).size).toBe(4);
    expect(ShapeRenderer.render('square', { rotate: 30 }))
      .not.toBe(ShapeRenderer.render('square'));
  });

  it('never lets a losange look like a square, at any rotation or scale', () => {
    // A rhombus with equal diagonals IS a square, and a CP pupil cannot tell
    // them apart. The losange therefore has a 5:3 diagonal ratio, and that
    // ratio must survive every transform.
    for (const rotate of ALL_ROTATIONS) {
      for (const scale of ALL_SCALES) {
        const [long, short] = diagonals(ShapeRenderer.render('rhombus', { rotate, scale }));
        expect(long / short).toBeCloseTo(5 / 3, 2);
      }
    }
  });

  it('gives the square and the rectangle equal diagonals, as they must have', () => {
    for (const shape of ['square', 'rectangle']) {
      for (const rotate of ALL_ROTATIONS) {
        const [a, b] = diagonals(ShapeRenderer.render(shape, { rotate }));
        expect(a / b).toBeCloseTo(1, 2);
      }
    }
  });

  it('leaves a circle unchanged by rotation, because a circle has no orientation', () => {
    const base = circleGeometry(ShapeRenderer.render('circle', { scale: 1.3 }));
    for (const rotate of ALL_ROTATIONS) {
      expect(circleGeometry(ShapeRenderer.render('circle', { rotate, scale: 1.3 })))
        .toEqual(base);
    }

```js
const SIZE = 200;
const CX = SIZE / 2;
const CY = SIZE / 2;
// Circumradius at scale 1. Chosen so that the largest scale the shapes game
// asks for (1.5) still leaves the figure inside the 200x200 frame: 60 * 1.5 =
// 90 < 100. Because every shape below is normalised to this circumradius,
// containment holds at every rotation without any per-shape special-casing.
const FIT = 60;

// Unit outlines, centred on the origin, y pointing down as in SVG. Each is
// normalised by its own largest vertex radius when rendered, so all four end up
// inscribed in the same circle.
//   square    — axis-aligned, flat-bottomed at rotation 0
//   rectangle — 1.75:1, unmistakably not a square
//   triangle  — equilateral, point up at rotation 0
//   rhombus   — a losange with a 5:3 diagonal ratio. Equal diagonals would make
//               it a square standing on its corner, which a CP pupil cannot
//               tell from `carré`, so the ratio is deliberately not 1.
const UNIT = {
  square: [[-1, -1], [1, -1], [1, 1], [-1, 1]],
  rectangle: [[-1.75, -1], [1.75, -1], [1.75, 1], [-1.75, 1]],
  triangle: [[0, -1], [0.866, 0.5], [-0.866, 0.5]],
  rhombus: [[0, -1], [0.6, 0], [0, 1], [-0.6, 0]],
};

export const SHAPE_KEYS = ['square', 'rectangle', 'triangle', 'circle', 'rhombus'];
export const SHAPE_SIDES = { square: 4, rectangle: 4, triangle: 3, circle: 0, rhombus: 4 };
export const SHAPE_CORNERS = { square: 4, rectangle: 4, triangle: 3, circle: 0, rhombus: 4 };

export const ShapeRenderer = {
  // shape: one of SHAPE_KEYS. options: { rotate (degrees), scale, fill, stroke }.
  // Rotation and scale are baked into the coordinates rather than applied as an
  // SVG transform, so the emitted markup is self-describing and a test can read
  // the real vertex positions straight out of it.
  render(shape, options = {}) {
    const rotate = Number.isFinite(options.rotate) ? options.rotate : 0;
    const scale = Number.isFinite(options.scale) && options.scale > 0 ? options.scale : 1;
    const fill = options.fill || '#ffd54f';
    const stroke = options.stroke || '#2e5c8a';

    let key = 'unknown';
    let body = '';

    if (UNIT[shape]) {
      key = shape;
      body = renderPolygon(UNIT[shape], rotate, scale, fill, stroke);
    } else if (shape === 'circle') {
      key = 'circle';
      body = renderCircle(scale, fill, stroke);
    }

    return '<svg width="' + SIZE + '" height="' + SIZE +
      '" viewBox="0 0 ' + SIZE + ' ' + SIZE +
      '" class="shape-figure dice-enter" data-shape="' + key +
      '" data-rotate="' + rotate + '" data-scale="' + scale + '">' + body + '</svg>';
  },
};

function renderPolygon(unit, rotate, scale, fill, stroke) {
  const norm = Math.max(...unit.map(([x, y]) => Math.hypot(x, y)));
  const r = FIT * scale / norm;
  const rad = rotate * Math.PI / 180;
  const cos = Math.cos(rad);
  const sin = Math.sin(rad);

  const points = unit.map(([x, y]) =>
    round(CX + r * (x * cos - y * sin)) + ',' + round(CY + r * (x * sin + y * cos))
  ).join(' ');

  return '<polygon class="shape-poly" points="' + points +
    '" fill="' + fill + '" stroke="' + stroke +
    '" stroke-width="5" stroke-linejoin="round"/>';
}

function renderCircle(scale, fill, stroke) {
  return '<circle class="shape-circle" cx="' + CX + '" cy="' + CY +
    '" r="' + round(FIT * scale) + '" fill="' + fill +
    '" stroke="' + stroke + '" stroke-width="5"/>';
}

function round(value) {
  return Math.round(value * 100) / 100;
}

Each exercise: `{ shape, rotate, scale, mode, bodyClass, correctAnswer, promptHtml, choices }`. `mode` is `'name'` (easy and hard) or `'sides'`/`'corners'` (normal). On `'name'` exercises `correctAnswer` is the shape **key** and `choices` is five `{ value, html }` objects — the key as the value, the translated label as the html — exactly the seam `compare` uses for its signs. On counting exercises `correctAnswer` is a number and `choices` is five plain numbers. `bodyClass` is `'shape-name-mode'` or `'shape-count-mode'`, which is what lets the CSS give the five word-buttons a two-column grid and the five number-buttons the default five-column one. Also produces the CSS classes `.shape-game-layout`, `.shape-figure`, `.shape-choice-btn`, `body.shape-name-mode` and `body.shape-count-mode`.

**`shapes` is the first and only game in the `geometrie` domain.** `gamesByDomain()` filters out empty domains, so the 🔷 *Espace et géométrie* group appears in the chooser for the first time with this task, sitting **third**, between *Grandeurs et mesures* and *Logique*. That shifts the array indices `test/engine/registry.test.js` uses, and it makes the existing test `it('leaves geometrie empty until Tier 3 adds shapes', ...)` false — Step 5 replaces it rather than deleting the coverage.

Ladder: easy names the shape (untransformed); normal counts sides or corners (untransformed); hard names the shape **rotated and rescaled**.

**Why hard is genuinely about invariance.** A child who has learned "a square is the flat-bottomed one" must be caught out, so the hard band draws its rotation from a fixed list of multiples of 15° with **every multiple of 45° removed**. Multiples of 90° would leave a square or rectangle axis-aligned — not rotated at all, from the child's point of view — and 45°/135°/225°/315° would stand a square on its corner, where a CP pupil genuinely cannot tell `carré` from `losange`. That is not a fair question, so it is excluded. The scale list excludes `1`, so the band always rescales too. And the circle is left out of the hard shape pool: it is invariant under rotation by definition, so a circle round would be a free point in the one band that is supposed to be hard.

**Shuffle-test shape: B (positions grouped per correct-answer value), all three bands.** Choices are built by shuffling a **fixed list** — `SHAPE_KEYS` on the naming bands, `COUNT_CHOICES` on the counting band — while `correctAnswer` varies. Ungrouped, `indexOf(correctAnswer)` therefore takes a different value per shape *even with the shuffle deleted* (`square` → 0, `rectangle` → 1, `triangle` → 2 …), so `positions.size > 1` passes vacuously. This is the `compare` situation exactly (`test/games/compare.test.js:73-88`). Grouping by the answer's own value pins each group to a single index on unshuffled code and goes red deterministically. Shape A does **not** apply and must not be used here.

import { ShapeRenderer, SHAPE_KEYS, SHAPE_SIDES, SHAPE_CORNERS } from '../render/shapes.js';

const NAME_KEYS = {
  square: 'shapeSquare',
  rectangle: 'shapeRectangle',
  triangle: 'shapeTriangle',
  circle: 'shapeCircle',
  rhombus: 'shapeRhombus',
};

// Multiples of 15 degrees with every multiple of 45 removed. 0/90/180/270 leave
// a square or rectangle axis-aligned, so the child never has to see past the
// turn; 45/135/225/315 stand a square on its corner, where `carré` and
// `losange` are the same picture to a six-year-old and the question stops being
// fair. Neither belongs in the band whose whole point is invariance.
const HARD_ROTATIONS = [
  15, 30, 60, 75, 105, 120, 150, 165, 195, 210, 240, 255, 285, 300, 330, 345,
];
// Never 1 — the hard band must actually rescale as well as rotate.
const HARD_SCALES = [0.6, 0.75, 1.3, 1.5];
// A circle is invariant under rotation by definition, so a circle round in the
// hard band is a free point. It stays in easy and normal, where "no sides" is
// the thing being taught.
const HARD_SHAPES = ['square', 'rectangle', 'triangle', 'rhombus'];
// Fixed count options. Every true answer is 0, 3 or 4, so the correct value is
// always present and the distractors never move.
const COUNT_CHOICES = [0, 2, 3, 4, 5];

export const ShapesGame = {
  id: 'shapes',
  nameKey: 'shapes',
  emoji: '📐',
  domain: 'geometrie',
  rounds: { easy: 5, normal: 10, hard: 20 },
  layoutClass: 'shape-game-layout',
  choiceClass: 'shape-choice-btn',

  generate(difficulty, ctx) {
    const { rng, t, count } = ctx;
    const exercises = [];

    for (let i = 0; i < count; i++) {
      if (difficulty === 'normal') {
        exercises.push(countExercise(rng, t));
      } else if (difficulty === 'hard') {
        exercises.push(nameExercise(
          rng, t, HARD_SHAPES, pick(HARD_ROTATIONS, rng), pick(HARD_SCALES, rng)
        ));
      } else {
        exercises.push(nameExercise(rng, t, SHAPE_KEYS, 0, 1));
      }
    }

    return exercises;
  },
};

function nameExercise(rng, t, pool, rotate, scale) {
  const shape = pick(pool, rng);

  return {
    shape,
    rotate,
    scale,
    mode: 'name',
    bodyClass: 'shape-name-mode',
    correctAnswer: shape,
    promptHtml:
      ShapeRenderer.render(shape, { rotate, scale }) +
      '<div class="op-hint">' + t('shapesNamePrompt') + '</div>',
    // Object-form choices: the English key travels as the value so the answer
    // never depends on the active language, the translated word is what the
    // child reads. The same seam compare uses for its < = > signs.
    choices: shuffle(
      SHAPE_KEYS.map(key => ({ value: key, html: t(NAME_KEYS[key]) })),
      rng
    ),
  };
}

function countExercise(rng, t) {
  const shape = pick(SHAPE_KEYS, rng);
  const countSides = rng() < 0.5;

  return {
    shape,
    rotate: 0,
    scale: 1,
    mode: countSides ? 'sides' : 'corners',
    bodyClass: 'shape-count-mode',
    correctAnswer: countSides ? SHAPE_SIDES[shape] : SHAPE_CORNERS[shape],
    promptHtml:
      ShapeRenderer.render(shape) +
      '<div class="op-hint">' +
        t(countSides ? 'shapesSidesPrompt' : 'shapesCornersPrompt') +
      '</div>',
    choices: shuffle(COUNT_CHOICES.slice(), rng),
  };
}

function pick(items, rng) {
  return items[Math.floor(rng() * items.length)];
}

function shuffle(items, rng) {
  for (let i = items.length - 1; i > 0; i--) {
    const j = Math.floor(rng() * (i + 1));
    [items[i], items[j]] = [items[j], items[i]];
  }

  return items;
}

`parity` joins the `nombres` domain as its **twelfth** card, after `word_problems`.

Ladder: easy ≤ 10 with the objects shown in pairs; normal a numeral ≤ 20; hard a numeral ≤ 100.

**Why easy shows pairs.** Even and odd is not a rule to memorise at CP; it is "does everyone have a partner?". The easy band therefore draws the number as `floor(n / 2)` two-object pairs plus, when `n` is odd, one visibly lonely single. The odd one out must be *unpaired on screen*, not merely present, which is why the leftover gets its own `.parity-lonely` container rather than being appended into the last pair. The object set is chosen through `ctx.rng` from `OBJECT_CATEGORIES` — **no category pre-screen**, unlike `count_objects`.

**Shuffle-test shape: B (positions grouped per correct-answer value) — mandatory and non-negotiable.** With only **two** fixed choices, the ungrouped test is not merely weak, it is *guaranteed* to pass on unshuffled code. `ANSWERS` is the constant `[even, odd]`, so with the shuffle deleted `indexOf('even')` is always `0` and `indexOf('odd')` is always `1`; the position set is `{0, 1}`, `size === 2 > 1`, green. `compare`'s three choices made this trap likely; two choices make it certain. Grouping by the answer's own value pins each group to exactly one index on unshuffled code — `{0}` for even, `{1}` for odd — and the assertion goes red deterministically. Step 10 demonstrates the vacuity rather than only claiming it.

import { OBJECT_CATEGORIES } from './object-categories.js';

const MAX = { easy: 10, normal: 20, hard: 100 };

// Two choices only. The English keys travel as the values so the answer never
// depends on the active language; the translated words are what the child reads.
const ANSWERS = [
  { value: 'even', labelKey: 'parityEven' },
  { value: 'odd', labelKey: 'parityOdd' },
];

export const ParityGame = {
  id: 'parity',
  nameKey: 'parity',
  emoji: '🧦',
  domain: 'nombres',
  rounds: { easy: 5, normal: 10, hard: 20 },
  layoutClass: 'parity-layout',
  choiceClass: 'parity-choice-btn',

  generate(difficulty, ctx) {
    const { rng, t, count } = ctx;
    const max = MAX[difficulty];
    const exercises = [];

    for (let i = 0; i < count; i++) {
      const number = 1 + Math.floor(rng() * max);
      // The object set is drawn here rather than asked for on a pre-screen: a
      // six-year-old should reach the first question in one tap.
      const category = OBJECT_CATEGORIES[Math.floor(rng() * OBJECT_CATEGORIES.length)];
      const emoji = category.emojis[Math.floor(rng() * category.emojis.length)];
      const showObjects = difficulty === 'easy';

      exercises.push({
        number,
        emoji: showObjects ? emoji : null,
        correctAnswer: number % 2 === 0 ? 'even' : 'odd',
        promptHtml:
          (showObjects
            ? renderPairs(number, emoji)
            : '<div class="op-question">' + number + '</div>') +
          '<div class="op-hint">' + t('parityPrompt') + '</div>',
        choices: shuffle(
          ANSWERS.map(answer => ({ value: answer.value, html: t(answer.labelKey) })),
          rng
        ),
      });
    }

    return exercises;
  },
};

// Even and odd is not a rule to memorise at CP, it is "does everyone have a
// partner?". So the objects are laid out as complete pairs, and an odd number
// leaves exactly one object visibly alone in its own container rather than
// tucked into the last pair.
function renderPairs(number, emoji) {
  let out = '<div class="parity-pairs">';

  for (let i = 0; i + 1 < number; i += 2) {
    out += '<div class="parity-pair">' +
      '<span class="parity-object">' + emoji + '</span>' +
      '<span class="parity-object">' + emoji + '</span>' +
    '</div>';
  }

  if (number % 2 === 1) {
    out += '<div class="parity-pair parity-lonely">' +
      '<span class="parity-object">' + emoji + '</span>' +
    '</div>';
  }

  return out + '</div>';
}

function shuffle(items, rng) {
  for (let i = items.length - 1; i > 0; i--) {
    const j = Math.floor(rng() * (i + 1));
    [items[i], items[j]] = [items[j], items[i]];
  }

  return items;
}

**Interfaces:**
- Consumes: the `.op-hint` CSS from checkpoint 2. Nothing from Tasks 1–3.
- Produces: `OrderingGame` (named export from `js/games/ordering.js`) with `id: 'ordering'`, `nameKey: 'ordering'`, `emoji: '🪜'`, `domain: 'nombres'`, `rounds: { easy: 5, normal: 10, hard: 20 }`, `layoutClass: 'ordering-layout'`, and a `renderChoices(el, exercise, submit)`. **No `renderPrompt`, no `isCorrect`, no `choiceClass`, no `legacy`.** Each exercise: `{ numbers, ordered, descending, correctAnswer, promptHtml }` — `numbers` is the display order (a shuffle of the draw), `ordered` the required tap order, `correctAnswer` is `ordered.join(',')`. Also produces the CSS classes `.ordering-layout`, `.ordering-arrow`, `.ordering-tile`, `.ordering-value` and `.ordering-rank`.

`ordering` joins the `nombres` domain as its **thirteenth** card, after `parity`, and completes the twelve-game programme.

Ladder: easy 3 numbers ≤ 20 ascending; normal 5 numbers ≤ 100 ascending; hard 5 numbers ≤ 100 **descending**.

**Read "The `ordering` design question, resolved" in the Global Constraints before writing a line of this task.** In short: this is the project's first sequencing interaction, and it fits the existing engine because `renderChoices` accumulates taps in a closure and calls `submit(...)` **exactly once per attempt, with no `btn` argument**. With `btn === undefined`, `GameEngine.answer()` (`js/engine/game-engine.js:131-173`) never enters `if (btn && btn.dataset.wrongChoice)` and never executes `btn.dataset.wrongChoice = '1'`, so the latch that forced `memory` to become `legacy: true` is never reached and no tile is ever taken out of play. `correctAnswer` is the required ordering joined with commas, so the engine's default `value === exercise.correctAnswer` already compares the two orderings exactly and **no `isCorrect` seam is needed**. `js/engine/game-engine.js` is not touched.

**Answer uniqueness.** `numbers` never contains a duplicate. With a tie the ordering would have two correct tap sequences and one of them would be judged wrong, so `pickDistinct` rejects repeats and a test asserts it directly.

**Shuffle-test shape: A (ungrouped `indexOf`), measured per difficulty in its own `Set`.** `pickDistinct` returns its draw **sorted**, and `numbers` is an explicit `shuffle` of that sorted array. Without the shuffle the first number the child must tap sits at a fixed index — `0` on the two ascending bands, `size - 1` on the descending one. Each band therefore collapses to a single position and goes red deterministically. **The bands must not be pooled into one `Set`:** pooled, the unshuffled code would yield `{0, 4}`, `size === 2 > 1`, and the test would pass vacuously. This is the same trap as Shape B, arriving through a different door.

- [ ] **Step 3: Write the game**

Create `js/games/ordering.js`:

```js
const CONFIG = {
  easy: { size: 3, max: 20, descending: false },
  normal: { size: 5, max: 100, descending: false },
  hard: { size: 5, max: 100, descending: true },
};

// How long the broken sequence stays red before the board clears itself. Long
// enough for a six-year-old to see which tap went wrong, short enough that the
// retry does not feel like a punishment.
const RESET_DELAY_MS = 500;

export const OrderingGame = {
  id: 'ordering',
  nameKey: 'ordering',
  emoji: '🪜',
  domain: 'nombres',
  rounds: { easy: 5, normal: 10, hard: 20 },
  layoutClass: 'ordering-layout',

  generate(difficulty, ctx) {
    const { rng, t, count } = ctx;
    const config = CONFIG[difficulty];
    const exercises = [];

    for (let i = 0; i < count; i++) {
      // pickDistinct returns its draw sorted, so the display order below is the
      // result of one explicit shuffle. That is what makes the shuffle testable:
      // delete it and the first number to tap sits at a fixed index.
      const sorted = pickDistinct(config.size, config.max, rng);
      const ordered = config.descending ? sorted.slice().reverse() : sorted.slice();

      exercises.push({
        numbers: shuffle(sorted.slice(), rng),
        ordered,
        descending: config.descending,
        // The whole ordering as one string. The engine's default
        // `value === exercise.correctAnswer` then compares the tapped ordering
        // against the required one with no custom isCorrect needed.
        correctAnswer: ordered.join(','),
        promptHtml:
          '<div class="ordering-arrow">' + (config.descending ? '⬇️' : '⬆️') + '</div>' +
          '<div class="op-hint">' +
            t(config.descending ? 'orderingDescPrompt' : 'orderingAscPrompt') +
          '</div>',
      });
    }

    return exercises;
  },

  // The project's only sequencing interaction. Taps accumulate in `picked` and
  // the engine is told the verdict exactly ONCE per attempt, deliberately
  // without a `btn`: GameEngine.answer(value, btn) only reaches its
  // `dataset.wrongChoice` latch when `btn` is truthy, so passing none means no
  // tile is ever taken out of play and the exercise always stays completable.
  // The engine still owns the sound, the attempt count and the advance; this
  // function owns only the visuals and the retry reset.
  renderChoices(el, exercise, submit) {
    const picked = [];
    let locked = false;

    el.innerHTML = exercise.numbers.map(value =>
      '<button class="choice-btn ordering-tile" data-value="' + value + '">' +
        '<span class="ordering-value">' + value + '</span>' +
        '<span class="ordering-rank"></span>' +
      '</button>'
    ).join('');

    const tiles = [...el.querySelectorAll('.ordering-tile')];

    const reset = () => {
      picked.length = 0;
      locked = false;
      tiles.forEach(tile => {
        delete tile.dataset.picked;
        tile.classList.remove('picked', 'wrong');
        tile.querySelector('.ordering-rank').textContent = '';
      });
    };

    tiles.forEach(tile => {
      tile.addEventListener('click', () => {
        if (locked || tile.dataset.picked) return;

        const value = Number(tile.dataset.value);

        if (value !== exercise.ordered[picked.length]) {
          // `.wrong` alone, never `dataset.wrongChoice`. The class picks up the
          // app's shared red shake from `.choice-btn.wrong`; the dataset flag is
          // the engine's private latch and must stay the engine's business.
          locked = true;
          tile.classList.add('wrong');
          submit(picked.concat(value).join(','));
          setTimeout(reset, RESET_DELAY_MS);

          return;
        }

        picked.push(value);
        tile.dataset.picked = '1';
        tile.classList.add('picked');
        tile.querySelector('.ordering-rank').textContent = picked.length;

        if (picked.length === exercise.ordered.length) {
          // The engine skips `btn.classList.add('correct')` when no button was
          // passed, so the finished sequence colours itself.
          locked = true;
          tiles.forEach(other => other.classList.add('correct'));
          submit(picked.join(','));
        }
      });
    });
  },
};

// A repeat would give the exercise two correct tap sequences, one of which the
// engine would judge wrong, so repeats are rejected rather than tolerated.
function pickDistinct(size, max, rng) {
  const out = [];
  let guard = 0;

  while (out.length < size && guard < 500) {
    const value = 1 + Math.floor(rng() * max);
    if (!out.includes(value)) out.push(value);
    guard++;
  }

  // A degenerate rng — a seeded test stub returning a constant, say — starves
  // the rejection loop above and would leave a board of one tile. Top up
  // deterministically so the count always matches the difficulty ladder: a
  // short board would silently contradict "3 numbers" or "5 numbers".
  for (let value = 1; out.length < size && value <= max; value++) {
    if (!out.includes(value)) out.push(value);
  }

  return out.sort((a, b) => a - b);
}

function shuffle(items, rng) {
  for (let i = items.length - 1; i > 0; i--) {
    const j = Math.floor(rng() * (i + 1));
    [items[i], items[j]] = [items[j], items[i]];
  }

  return items;
}

The guard that catches this lives in the **engine-driven** describe block, not the DOM-only one: the DOM-only tests call a `vi.fn()` stub, which never sets `dataset.wrongChoice`, so its `toBeUndefined()` assertion only guards against the *game* setting the flag itself.

Every later wrong tap of that same tile then hits `if (btn && btn.dataset.wrongChoice)`, re-shakes and returns **before** `this.wrongAttempts++`, so three genuine wrong attempts are scored as one. The scoring corruption is silent — nothing on screen looks different — which is exactly the kind of bug that ships.

Note what does **not** happen, because the plan should not overstate the danger: the session still completes. `ordering` decides for itself which taps it accepts, so a latched tile is still tappable as part of a correct sequence and the exercise never deadlocks the way `memory`'s board did. The reason to pass no button is therefore not "otherwise it deadlocks" but "otherwise the engine keeps per-button state about an interaction that has no per-button semantics, and the wrong-attempt count silently drifts".
