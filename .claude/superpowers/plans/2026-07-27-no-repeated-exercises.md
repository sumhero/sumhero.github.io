# No Repeated Exercises Within a Session — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stop the fifteen engine-driven games that can currently repeat an exercise inside one session from doing so, by drawing every exercise without replacement through one new shared helper, with **no change to `js/engine/game-engine.js`**.

**Architecture:** One new pure module, `js/engine/unique.js`, exporting `drawDistinct(count, draw, keyOf, tries)` — a **bounded rejection sampler** that never enumerates the question space, so each game's own validity rules (`shapes`' 45° square exclusion, `chess`'s zero-target knight, `word_problems`' two-step floors) stay in the one place they already live. Each game then wraps its existing per-round body in a `draw(i)` closure over `ctx.rng` and names its own identity key. When a round exhausts its try budget — which is the *normal* state for the games whose round count exceeds their question space — the used-set is cleared and **re-seeded with the exercise just emitted**, so the fresh pass can never place a repeat immediately after its previous showing. Behaviour degrades exactly to "cycle the whole space evenly, never twice in a row", and the loop is bounded so it cannot hang.

**Tech Stack:** Plain ES modules (no bundler, no transpilation), Vitest + jsdom for tests, service worker generated by `tools/build-sw.js`.

## Global Constraints

Every task's requirements implicitly include this section.

- **The `ctx` purity rule** (verbatim from `CLAUDE.md`). A game's `generate` must be **pure**: no `Math.random`, no `I18n`, no DOM access, no `Date`.
  - `ctx.rng` is the only source of randomness — normally `Math.random`, but tests inject a seeded rng, so `generate` must call `ctx.rng()` and never `Math.random()` directly.
  - `ctx.t` is the only source of translated strings — `(key, params) => I18n.t(key, params)` — so `generate` must call `ctx.t(...)` and never `I18n` directly.
  - `ctx.lang` is the active language code, for anything language-dependent that isn't a plain translation lookup.
  - `ctx.count` is the already-resolved round count for the chosen difficulty (`GameEngine.resolveCount` reads `game.rounds[difficulty]`, or passes through the picker's choice when `rounds === 'ask'`) — `generate` must use `ctx.count` and never read `game.rounds` itself, or a picker game and a fixed-rounds game would silently diverge.
  - `ctx.category` is set only for `setup: 'category'` games.
  - **The new helper is bound by the same rule.** `js/engine/unique.js` must contain no `Math.random`, no `Date`, no DOM and no `I18n`. It receives all randomness indirectly, through the `draw` closure the game hands it, which closes over `ctx.rng`. It takes no rng of its own.
- **No frameworks, no bundler, no transpilation** — keep it plain ES that runs directly in the browser. Match the existing style (2-space indent, single quotes, string-concatenated HTML).
- **`sw.js` is generated** — never hand-edit it, and never hand-bump `CACHE_VERSION`. Run `npm run build:sw` (`tools/build-sw.js`), which scans `js/`, `css/`, `images/`, and `flags/` for the asset list and computes the next `CACHE_VERSION` itself (same day → bump the counter, new day → reset to `01`). A hand-edit to `sw.js` will be silently overwritten the next time the build runs. **`test/tools/build-sw.test.js` goes red the moment a new file under `js/` is committed without regenerating `sw.js`** — this was reproduced while writing this plan, so **Task 1 must run `npm run build:sw` in the same commit that adds `js/engine/unique.js`.**
- **`test/i18n/no-dead-keys.test.js` asserts all five language blocks have an identical key set**, so a key added to one block must be added to all five in the same commit. **This work adds no translation keys at all** — no prompt text changes. If a task finds itself editing `js/i18n/translations.js`, stop and report it.
- **`js/engine/game-engine.js` must not be touched.** It has been byte-identical since checkpoint 1 across three checkpoints, and nothing here needs it. The tempting engine-side "over-generate `count * 3` and filter down via a new `exerciseKey` seam" design is **explicitly rejected** for three concrete reasons: it breaks index-dependent generators (`number_words` alternates its irregular French 70–99 band on even `i`; `count_objects` cycles emoji on `i`; `dice_addition` sorts by sum *after* generation and would be truncated post-sort); it still cannot guarantee the count when the space is smaller than the round count, so it needs the fallback logic anyway, only split across two files; and it triples generation cost, building and discarding every SVG die, clock, ten-frame, base-ten block and coin purse twice. **A task that believes it needs an engine change must stop and report it rather than making one.** Verify with `git diff --stat js/engine/game-engine.js` before every commit — it must be empty.
- **`css/game.css` must not be touched by this plan.** Another agent is editing it concurrently on `main`. Nothing here is a visual change. **If a task appears to need a CSS change, stop and flag it rather than editing the file.**
- **Testing discipline** (verbatim intent from `CLAUDE.md`). Prove a new test can fail before trusting it: break the code it names, confirm the test goes red, then restore the code and confirm `git diff` is empty. If a test depends on randomness, either seed the rng and assert an exact result, or run the mutation **10 times** and require red on all ten — a guard that only sometimes catches its mutation is worse than no guard. Prefer asserting the property over the implementation.
- **No test may import a constant from the module it is guarding in order to build its own expectation.** This project shipped a tautological guard that way — a test asserting `>= MIN_TWO_STEP_TOTAL` while the generator floored on that same constant, which left every test green when the constant was lowered to a broken value. Guards state their expected value as an **independent literal, deliberately duplicated**, with a comment saying why. Importing a constant in order to compare it *against* a literal (`expect(DRAW_TRIES).toBe(40)`) is the opposite and is required; deriving an expectation *from* it (`expect(draws).toBeLessThan(DRAW_TRIES * 2)`) is banned.
- **`DRAW_TRIES` is 40 and must not be changed casually.** See "Why the budget is exactly 40" below — 30 or 50 would leave `test/games/chess.test.js`'s anti-repeat test **silently vacuous** rather than red, which is worse than breaking it.
- **Workflow.** This work runs on branch `worktree-no-repeats` in the worktree at `.claude/worktrees/no-repeats`, and merges to `main` once green. Run `npm test` before every commit; never commit a red suite. Baseline at the start of this plan: **41 files, 496 tests passing.**

## The rule (decided — do not re-litigate)

> Draw each exercise without replacement from the game's own question space using a **bounded** rejection sampler. When the space is exhausted — detected by the try budget running out, never by enumerating the space — clear the used-set and start a fresh pass, but **re-seed it with the last exercise emitted**, so the wrap-around can never place a repeat next to its previous occurrence.

Two candidate rules were rejected and must not be reintroduced:

- **"Never repeat consecutively"** — already implemented in five games, and those five still misbehave: `guess_time` hard shows a triple in 7.9% of sessions and `chess` hard in 30.7%, *with* the guard in place. `A B A B A` reads to a six-year-old exactly as badly as `A A A`. One slot of memory is not enough.
- **"Stop deduplicating once exhausted"** — after exhaustion `dice_recognition` hard would revert to uniform random for its last fifteen rounds and could still emit `3 3 3`.

**Key on the whole exercise, never on `correctAnswer`.** Answer-keying is wrong for twelve of the twenty engine-driven games and actively harmful in five: `parity` has only two possible answers (`'even'`/`'odd'`), `compare` only three (`lt`/`eq`/`gt`), `shapes`' count band only three real values, `chess`'s answer is a *set* of legal squares matched by a custom `isCorrect`, and `money` hard's answer space (18) is smaller than its round count (20). There is therefore **no useful engine-level default key** — each game names its own. That per-game cost is irreducible and is the main reason a purely central fix is not available.

## Why the budget is exactly 40

`DRAW_TRIES = 40` is a hard constraint, not a taste call. Three things pin it:

1. **Large enough.** 40 tries completes a permutation of 20 with high probability. Measured over 500 000 simulated sessions (see the table below), no configuration in the app ever produced an adjacent repeat, and every space smaller than the round count was covered completely.
2. **Small enough.** Every existing `it('is deterministic for a fixed rng')` test drives `generate` with a **constant** rng (`() => 0.5`), which makes every rejection loop miss on every retry and burn its whole budget on every round. The existing guards in this codebase are 200 and 500; at 500 the suite would slow measurably. At 40 the whole suite stayed at ~4 s in the prototype run.
3. **40 keeps `test/games/chess.test.js`'s mutation argument valid, and 30 or 50 would silently destroy it.** That test drives `generate` with a 12-value cycling rng and relies on a mutant burning `tries × 3 rng draws` and landing back on cycle position 0. `500 × 3 = 1500` is a multiple of 12; `40 × 3 = 120` is also a multiple of 12; `30 × 3 = 90` and `50 × 3 = 150` are **not**. This was verified by prototyping: with `tries = 40` the mutant reproduces exercise 0 as exercise 1 and the test goes red; with `tries = 30` or `50` the mutant produces the *correct* output and the test passes on broken code. **Any future change to `DRAW_TRIES` must re-run the chess mutation in Task 5, Step 8.**

## Identity key, per game

`keyOf` must always return a **string**. Mixing numbers and strings in one `Set` is a latent bug.

| game | `keyOf(exercise)` | why not `correctAnswer` |
|---|---|---|
| `dice_recognition` | `String(exercise.correctAnswer)` | coincides — the face value *is* the question |

## Where deduplication fights an existing guarantee

Each of these was checked against the code. The rejection-sampler shape preserves all of them for free; a pool-shuffle design would have destroyed most of them.

1. **`number_words` hard — the even-index irregular band.** `const irregular = difficulty === 'hard' && i % 2 === 0` (`js/games/number-words.js:33`) draws even rounds from 70–99 and odd rounds from 1–100, and `test/games/number-words.test.js` asserts the 50/50 split. **Resolution:** `drawDistinct` passes the round index `i` into `draw(i)`, so the band choice stays index-driven and the alternation is untouched. **One shared `used` Set across both bands is correct** — they overlap only on 70–99, and 10 even-index draws from a 30-value band is comfortably achievable (measured: 100% full-distinct in 500 000 sessions).
2. **`word_problems` — the two-step floors.** `MIN_TWO_STEP_TOTAL = 12` and `MIN_SPOKEN_COUNT = 2` are enforced inside `buildStory`/`addAddStory`/`addSubStory`. **Resolution:** a rejection wrapper only ever *rejects* a fully-built candidate, never constructs one, so every floor survives untouched. The key must be `kind:a:b:c` — answer-keying would leave hard's `addAdd` band with 9 reachable totals over 20 rounds and would thrash.
3. **`doubles` hard — the independent `asHalf` coin flip.** `rng() < 0.5` per round means the ten doubles and ten halves are never drawn in balance, so "20 rounds over a space of 20" is far less achievable than it looks. **Resolution:** the key is `kind:operand`, the coin flip stays inside `draw(i)`, and the test asserts **distinct ≥ 15**, never "all 20 distinct" — 14.4% of sessions legitimately refill. This is the one place where the plan deliberately accepts a non-adjacent repeat.
4. **`shapes` hard — the 45° square-only rotation exclusion.** `HARD_ROTATIONS_SQUARE` drops multiples of 45 for squares only, because a square at 45° *is* a rhombus and the question would have two defensible answers. **Resolution:** safe under rejection sampling, because the rule stays inside `draw(i)`; it would have had to be re-derived a second time under pool enumeration and would have drifted.
5. **`ordering` — `pickDistinct`'s distinct-values requirement and deterministic top-up.** With a tie the ordering would have two correct tap sequences and one would be judged wrong. **Resolution:** `ordering` is **out of scope** and untouched, precisely so the top-up is not disturbed. Its measured repeat rate is already 0.0–0.9%.
6. **`compare` — the 20% equal rate.** `EQUAL_CHANCE = 0.2` means `eq` cases are only `max` of the `max²` ordered pairs, so deduplicating on `left:right` slightly *reduces* the observed `=` frequency. **Resolution:** accepted, and Task 8 requires a code comment saying so, since a future reader would otherwise read it as a regression and "fix" it back. On easy that is 10 eq-pairs against 5 rounds — harmless.
7. **`dice_addition` — dedup precedes the easy sort.** Not migrated (see the table above), but recorded here so a future migration preserves the order: dedup first, sort by sum afterwards.

## Test impact — verified, not assumed

Every claim below was checked by prototyping the helper and four game migrations in this worktree and running the real suite, then reverting.

- **The 18 `it('is deterministic for a fixed rng')` tests stay green.** They assert *self-consistency* (`generate(...)` equals `generate(...)` under the same `() => 0.5`), never a literal expected value, and `drawDistinct` is deterministic in `rng`. Confirmed by running the whole suite against the prototype.
- **The five existing consecutive-repeat tests are strengthened and stay green** — `test/games/complements.test.js:82`, plus the equivalents in `dice-recognition`, `guess-time`, `count-objects` and `chess`. All assert `keys[i] !== keys[i-1]`; the new rule implies the old one, so they pass unchanged and become regression anchors.
- **`test/games/chess.test.js:106` does *not* go red — and that is the more dangerous outcome.** The diagnosis predicted this file would be the one real casualty. It is not: with `tries = 40` the correct code still produces `queen(1,1)` then `rook(0,0)`, and all four literal assertions plus the key check pass unchanged. **The real hazard is silent vacuity.** The test's whole mutation argument is the arithmetic in its comment — "500 tries × 3 draws/try = 1500 draws … 1500 is a multiple of the 12-value cycle length". After migration that sentence is false. It happens to remain *true in substance* only because `40 × 3 = 120` is also a multiple of 12; at `tries = 30` or `50` the mutant produces the correct output and the test passes on broken code. Task 5 therefore **rewrites the comment to the new arithmetic and re-proves the mutation**, rather than leaving a green test whose stated reasoning no longer holds.
- **`test/games/dice-recognition.test.js:49`** drives hard (space 5) with a 2-value cycling rng `[0.1, 0.9]` for 5 rounds. Its assertion (`ex.promptHtml === DiceRenderer.render(ex.correctAnswer)`) is draw-independent, and the sampler terminates. Verified green against the prototype.
- **`test/games/money.test.js:173,192`** run 20 LCG seeds × `ctx(15, rng)` across all difficulties; on hard that is 15 rounds against a space of 18, inside the budget, and the invariants asserted are properties of `buildExactPurse`, which is untouched.
- **The "does not always place the correct answer at the same position" tests are the residual risk.** `guess-time`, `uno`, `tens-units`, `parity`, `shapes`, `compare` and others drive these with short cycling rngs; migration changes how many `rng()` calls each round consumes, so the phase of the cycle shifts. `guess-time` and `uno` were prototyped and stayed green. **Every game task below has an explicit step to run the game's whole existing test file**, and states the remediation if one collapses: **extend the cycling rng's value list, never weaken the assertion**.
- **`test/tools/build-sw.test.js` goes red** until `npm run build:sw` is run after `js/engine/unique.js` is added. Reproduced. Task 1 handles it.
- **`test/docs/claude-md.test.js`** asserts that every `` `js/...` `` path mentioned in `CLAUDE.md` exists on disk. It imposes no constraint on the documented list of engine seams, so documenting `drawDistinct` in Task 9 is safe as long as `js/engine/unique.js` exists by then — it does, from Task 1.

### Task 1: The `drawDistinct` helper

**Files:**
- Create: `js/engine/unique.js`
- Test: `test/engine/unique.test.js`
- Modify: `sw.js` (via `npm run build:sw`, never by hand)

**Interfaces:**
- Consumes: nothing. This module imports nothing.
- Produces, both named exports of `js/engine/unique.js`:
  - `DRAW_TRIES = 40` — the try budget. See "Why the budget is exactly 40".
  - `drawDistinct(count, draw, keyOf, tries = DRAW_TRIES) -> Array` — returns exactly `count` items. `draw(i)` is called with the zero-based round index and must return a fully-built exercise object. `keyOf(exercise)` must return a **string** naming the exercise's identity. Every game in Tasks 2–8 calls this with three arguments and never passes `tries`.

Create `js/engine/unique.js`:

```js
// Draw-without-replacement for one game session, as a bounded rejection
// sampler.
//
// `draw(i)` builds a whole candidate exercise for round `i`. It stays a
// closure over the game's own `ctx.rng`, which is what lets index-dependent
// generators keep working (number_words alternates its irregular French
// 70-99 band on even `i`) and lets each game's validity rules stay in the one
// place they already live (shapes' 45-degree square exclusion, chess's
// zero-target knight, word_problems' two-step floors). This module never
// enumerates the question space and never learns anything about it.
//
// `keyOf(exercise)` names the exercise's identity and must return a string.
// It is never `correctAnswer`: parity has two possible answers, compare three,
// and chess's answer is a set of squares. Each game names its own key.
//
// Exhaustion is normal, not exceptional: dice_recognition hard has five faces
// over twenty rounds. When a round burns its budget, the used-set is cleared
// and re-seeded with the exercise just emitted, so the fresh pass can never
// place a repeat immediately after its previous showing. Behaviour degrades
// to "cycle the whole space evenly, never twice in a row", which is also the
// pedagogically right answer at that size. Both passes are bounded, so this
// cannot hang even when only one candidate exists.
export const DRAW_TRIES = 40;

export function drawDistinct(count, draw, keyOf, tries = DRAW_TRIES) {
  const items = [];
  const used = new Set();
  let lastKey = null;

  for (let i = 0; i < count; i++) {
    let item = draw(i);
    let key = keyOf(item);
    let attempts = 1;

    while (used.has(key) && attempts < tries) {
      item = draw(i);
      key = keyOf(item);
      attempts++;
    }

    if (used.has(key)) {
      used.clear();
      if (lastKey !== null) used.add(lastKey);

      attempts = 0;
      while (used.has(key) && attempts < tries) {
        item = draw(i);
        key = keyOf(item);
        attempts++;
      }
    }

    used.add(key);
    lastKey = key;
    items.push(item);
  }

  return items;
}
```
